# Kotlin / Spring backend requirements

Status: proposed implementation contract for the simple conversation demo.

## 1. Scope and technology

Build one Spring Boot application using Kotlin, Gradle Kotlin DSL, Spring MVC, Spring Data JPA, Bean Validation, Flyway, PostgreSQL, and Spring AI with local Ollama. Run one backend instance. Responses are synchronous JSON containing a complete assistant reply.

Use Java 21 as the proposed runtime baseline. At project initialization, select and pin compatible stable Spring Boot, Spring AI, Kotlin, and Gradle versions using the official compatibility documentation. Import the Spring AI BOM. Do not independently select incompatible latest versions or use snapshots. Use Kotlin Spring/JPA plugins and the Kotlin JSON integration required by the selected Boot version.

Use the `spring-ai-starter-model-ollama` integration. Configure the Ollama URL and exact locally installed model name externally; the model name remains a deployment choice. No classifier, embeddings, moderation models, tools, RAG, or vector database are included in this phase.

## 2. Functional requirements

- A browser-generated UUID v4 in the `user_id` cookie identifies the anonymous user. The backend validates the cookie and never creates a replacement identity silently.
- An unknown valid UUID can list conversations and receives count zero and an empty list. Create its internal User row lazily on the first successful conversation creation.
- List all owned conversation previews and their count in one response. A preview contains id, title, and createdAt. Order by createdAt descending, then id ascending. Sending and renaming do not change ordering because there is no updatedAt.
- Return a selected conversation and all messages ordered by sequence ascending. System prompts are internal and are not stored as visible messages.
- New conversation is a frontend-only draft until the first message is submitted. The creation endpoint accepts that message, obtains a complete LLM response, and persists a conversation and its first two messages atomically.
- Generate the initial title deterministically from the first message: normalize whitespace, trim, and retain the first 80 Unicode code points. Manual rename is supported and never overwritten by later messages.
- Existing-conversation sends include prior conversation context. Persist the new user and assistant messages together only after successful generation. Return their server IDs and timestamps.
- Rename and permanently delete owned conversations. Deletion removes their messages in the same database transaction.
- A provider failure, blank reply, timeout, or persistence failure must not leave half a message exchange or an empty conversation.
- Every conversation operation enforces ownership. Missing and foreign conversations both return 404.
- One send may run per existing conversation. Conflicting send, rename, and delete operations return 409 while generation is running. Reads return the last committed history.
- Sending to different conversations may proceed concurrently, subject to Ollama capacity. Two first-message requests create two independent conversations. Exactly-once delivery and automatic retries are outside v1.

## 3. Data model

All IDs are UUIDs generated by the backend, except external_id, which comes from the cookie. Use Instant in Kotlin and PostgreSQL timestamptz for timestamps. Store enum values as readable strings.

### User — table app_user

| Field | Storage | Constraint |
| --- | --- | --- |
| id | uuid | primary key |
| external_id | uuid | unique, not null |
| created_at | timestamptz | not null |

### Conversation — table conversation

| Field | Storage | Constraint |
| --- | --- | --- |
| id | uuid | primary key |
| user_id | uuid | not null, FK app_user(id) |
| title | varchar(80) | not null, nonblank |
| created_at | timestamptz | not null |

### Message — table message

| Field | Storage | Constraint |
| --- | --- | --- |
| id | uuid | primary key |
| conversation_id | uuid | not null, FK conversation(id), ON DELETE CASCADE |
| sequence | bigint | not null, positive |
| role | varchar | not null, USER or ASSISTANT |
| content | text | not null, nonblank |
| created_at | timestamptz | not null |

Unique constraint: (conversation_id, sequence). Sequences start at 1; a successful exchange appends two consecutive messages. No updated_at, reply_to_message_id, status, or safety evaluation fields.

Indexes: unique app_user(external_id); conversation(user_id, created_at DESC, id ASC); unique message(conversation_id, sequence). The unique message index also supports history queries. Do not cascade saves through a large Conversation.messages collection; query messages separately.

## 4. HTTP contract

Base path `/api`. All endpoints require the user_id cookie. Bodies and responses use camelCase JSON; roles use lowercase `user` and `assistant`. Timestamps use UTC RFC 3339.

| Method and path | Request body | Success |
| --- | --- | --- |
| GET /conversations | none | 200 ConversationListResponse |
| POST /conversations | SendMessageRequest | 201 MessageExchangeResponse |
| GET /conversations/{id} | none | 200 ConversationHistoryResponse |
| POST /conversations/{id}/messages | SendMessageRequest | 200 MessageExchangeResponse |
| PATCH /conversations/{id} | RenameConversationRequest | 200 ConversationPreviewResponse |
| DELETE /conversations/{id} | none | 204, no body |

DTOs:

```text
SendMessageRequest(content: String)
RenameConversationRequest(title: String)
ConversationPreviewResponse(id: UUID, title: String, createdAt: Instant)
ConversationListResponse(conversationCount: Long, conversations: List<ConversationPreviewResponse>)
MessageResponse(id: UUID, role: MessageRole, content: String, createdAt: Instant)
ConversationHistoryResponse(conversation: ConversationPreviewResponse, messages: List<MessageResponse>)
MessageExchangeResponse(conversation: ConversationPreviewResponse, userMessage: MessageResponse, assistantMessage: MessageResponse)
ApiError(code: String, message: String)
```

Count equals the returned list size. Internal user IDs, sequence allocation, provider metadata, and system prompts are not exposed. Do not serialize JPA entities directly.

Validation defaults: message content must be nonblank and at most 20,000 Unicode code points; title must be nonblank and at most 80 code points after trimming. Preserve message content except trim leading/trailing whitespace before storage and inference. Enforce code-point limits explicitly rather than accidentally measuring UTF-16 code units. Malformed JSON, malformed path UUIDs, and validation failures return 400.

| HTTP | Example code | Meaning |
| --- | --- | --- |
| 400 | INVALID_REQUEST | Invalid body or path parameter |
| 401 | INVALID_USER_ID | Missing, malformed, or non-v4 identity cookie |
| 404 | CONVERSATION_NOT_FOUND | Missing or not owned |
| 409 | CONVERSATION_BUSY | Mutation already in progress |
| 422 | CONTEXT_TOO_LARGE | Current input cannot fit configured prompt limits |
| 502 | GENERATION_FAILED | Provider failure or invalid/blank generated text |
| 503 | MODEL_UNAVAILABLE | Ollama cannot be reached or selected model is unavailable |
| 504 | GENERATION_TIMEOUT | Configured generation deadline exceeded |
| 500 | INTERNAL_ERROR | Unexpected failure, including failed persistence |

Keep client errors generic; log useful technical context server-side without prompts or message text. Classify known provider failures; otherwise use the generic 502 mapping.

## 5. Architecture and package structure

One deployable application and one Gradle module. Organize by feature, with explicit API, application, and persistence boundaries within the conversation feature.

```text
  identity/

  conversation/
    api/
      ConversationController.kt

      dto/
    application/
      ConversationQueryService.kt
      ConversationCommandService.kt
      ConversationStore.kt
      ConversationMutationGuard.kt
      ConversationTitleFactory.kt

    persistence/

      MessageEntity.kt
      ConversationRepository.kt
      MessageRepository.kt
    model/
      MessageRole.kt
  llm/
    LlmGateway.kt
    SpringAiLlmGateway.kt
    PromptFactory.kt
    PromptMessage.kt
    PromptPolicy.kt
  error/
    ApiError.kt

  application.yml
  application-local.yml
  prompts/system.txt
  db/migration/V1__create_conversation_schema.sql
```

Dependency direction: controller → application services → repositories / LlmGateway. Spring AI types stay inside the llm package. API DTOs stay at the API boundary. Persistence entities stay internal; map them to immutable snapshots before leaving read transactions. Avoid adding an interface for every service. LlmGateway is an interface because the external model boundary needs a test substitute and may gain safety checks later.

## 7. Message generation and transaction boundaries

### Create conversation

1. Validate identity and input; derive title and build first prompt.
2. Call Ollama outside a database transaction.
3. Open a short write transaction: get/create User, insert Conversation, insert USER sequence 1 and ASSISTANT sequence 2.
4. Commit, map persisted values, and return 201. Any database failure rolls back all inserts.

### Send to existing conversation

1. Check ownership before acquiring the guard, so a foreign busy conversation still returns 404.
2. Acquire the conversation mutation guard without waiting; otherwise return 409.
3. In a short read transaction, recheck ownership and load the selected context plus current maximum sequence.
4. Build prompt and call Ollama with no database transaction/connection held for generation.
5. In a short write transaction, recheck ownership and expected maximum sequence, allocate the next two sequence values, and insert both messages atomically.
6. Commit, return 200, and release the guard in finally.

Rename/delete use the same guard and short write transactions. Use a separate transactional bean or explicit TransactionTemplate so Spring proxy self-invocation does not accidentally bypass transaction boundaries. Set open-in-view=false. GET history reads metadata and messages in one repeatable-read transaction to avoid mixed snapshots during deletion or sends. List count is derived from its loaded preview list.

No pending rows are necessary for this scope. If the process stops before commit, the exchange is absent. If the response is lost after commit, the client may not know it succeeded; recovering by reloading history is supported, duplicate-proof resubmission is deferred.

## 8. Spring AI and context

Use Spring AI ChatClient with its synchronous call path. PostgreSQL message rows are the authoritative history. Explicitly pass selected history to each call; do not also attach a memory advisor that automatically writes/duplicates messages.

Proposed context policy: at most the last 10 complete exchanges from this conversation, in sequence order. The UI still receives full stored history. Add the current input once. Drop oldest complete exchanges when exceeding a configurable prompt size budget. A character budget is a conservative application limit, not an exact token count: configure model context/output limits consistently for the chosen Ollama model and validate this with integration tests. If system prompt plus current input cannot fit the budget, return 422 before inference. Make this policy visible in developer documentation because older conversation details can be forgotten by the LLM.

Keep a fixed system prompt in resources/prompts/system.txt. Do not accept system instructions or provider options from the public API. Return plain text and reject blank responses.

The gateway is the future integration boundary for response evaluation; no safety implementation or extra tables are introduced now.

## 9. Configuration and running locally

- PostgreSQL URL, username, password through environment variables.
- Ollama base URL and model name through environment variables; fail startup validation if the model name is missing.
- Externalize generation timeout, context limits, and system prompt resource.
- Provision/pull the selected model before serving demo traffic; avoid implicit model downloads during a user request.
- Docker Compose starts PostgreSQL. Backend may run through Gradle and Ollama natively, which is convenient on macOS. If backend runs in a container, configure a reachable Ollama host explicitly.
- Align provider total request deadline and proxy/browser timeout so the server can return its own timeout response first. A socket read timeout alone is not a guaranteed end-to-end deadline.
- Apply Flyway migrations; use Hibernate schema validation rather than schema creation/update.
- Same-origin `/api` routing in deployment; use the Vue development proxy locally. Do not expose Ollama directly to the browser.
- Return Cache-Control: no-store for API responses. Validate same-origin mutation requests and require JSON request bodies where applicable.
- Cookie UUID possession grants access. There is no login, recovery, or cross-device identity in v1.
- Basic Actuator health for application/database and a separate model readiness check. Do not generate a model reply on every health probe or expose sensitive actuator endpoints publicly.
- Log request ID, operation, duration, and error code; do not log cookies, full prompts, or message bodies by default.

## 10. Verification and delivery criteria

Use JUnit 5 and Spring Boot test support. Testcontainers PostgreSQL verifies migrations, constraints, ownership filtering, and transaction rollback. Substitute a deterministic LlmGateway in API/workflow tests. Keep one optional local Ollama smoke test outside the default test suite.

Required meaningful cases:

1. Unknown valid identity lists zero conversations without creating a User row.
2. First successful send creates exactly one conversation and two ordered messages.
3. Follow-up prompt contains this conversation's selected history and current input exactly once.
4. Provider failure/timeout leaves no partial exchange; failed creation leaves no conversation.
5. A failure on the second message insert rolls back the entire exchange.
6. Foreign conversation access and mutations return 404 and do not call the LLM.
7. Two concurrent sends to one conversation cannot generate duplicate sequence values; the rejected request returns 409. Guard is released after failure.
8. Rename/delete conflict with active generation; deleting removes messages.
9. Two simultaneous first sends for one cookie resolve to one internal User row without a unique-key failure.
10. Unicode title/content validation, context trimming, and malformed identity/body/path handling follow the contract.

Delivery includes Gradle wrapper, source structure above, Flyway migration, local database Compose file, environment example without secrets, README run instructions, updated OpenAPI, and automated checks. This document specifies the implementation; it does not claim the code or tests already exist.
